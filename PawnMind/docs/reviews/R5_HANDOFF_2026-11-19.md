## 2. R5-A：先修安全与协议一致性（P0，离线）

### A1. 首次开局 prompt 与 run-change 分类

**需验证的条件性缺陷：** `RecordingSaveService.ConfirmNewGame()` 遇到 first-run prompt 时调用 `ConfirmPrompt()`，响应 `prompt_confirmed=true`，未实际新建 run；`ActionRouter.HandleWrite()` 却按 op 名 `confirm_new_game` 预先登记 `RunChangeRequested=true`。在 `RunChangePolicy.NoRun → NoRun` 场景会保留 `requested`，`FindPendingFor` / `FindUnconfirmedRunChange` 可能拒绝下一次真正的 `confirm_new_game`。现有 `R4_F1_01` 仅验证不驱逐旧证据，没有覆盖随后第二次确认能否成功。**必须先写可失败的集成回归，若现有代码已处理，则标 NOT_REPRODUCED 并不修改。**

目标语义：
- `prompt_confirmed` 是独立 UI 操作完成，**不是**“run-changing native start issued”；不可因它永久阻塞实际开局。
- 只有实际 `StartNewGame()` / `load` 等已请求或可能派发原生跨局动作时，才登记 `RunChangeRequested` 并执行防盲重试。
- 保留真正 new/load 的 run-id 对账、未确认操作阻塞与历史证据保留；绝不靠 revision/day/scene 猜测跨局完成。

测试：`R5_RUN_01` 首次 prompt → 确认 → 新局确认 → `NoRun → runId`；`R5_RUN_02` 同一 prompt 不重复；`R5_RUN_03` 真正 start 已派发但未确认时第二 start 被拒；`R5_RUN_04` run-id 不可读时不假成功；`R5_RUN_05` 真实 load 的原防护回归。必要时将“prompt 确认”和“开始新局”拆成语义明确的内部 operation 类型，但保持公开兼容，任何 API 变化须做 policy/hash 审计。

### A2. Sleep verifier：三次快速查询不能证明原生动作失败

**已验证源码风险：** `RecordingSaveService.TryResolveSleep()` 当前 `sleepPolls >= 3` 且 Day 未增长时判 `failed("day_not_changed")`，没有真实时间下限；同一个异步睡眠可能在极短时间内被判失败，然后允许再次派发，存在双推进风险。

要求：
- 保留 Day 真实增加 → `completed`；Day 不变只是“尚未观测到完成”，不是已证明无副作用。
- 引入可注入的单调时钟 / 异步阶段证据 / 可观测 no-op 原生证据；不允许用三次连续 readback 直接推断 `failed`。
- 到达观察窗口但无法证明原生没执行：返回 `uncertain` 或 `running + explicit timeout`，并保持防重复派发；如无安全恢复证据，要求人工干预，而不是强制自动重试。
- 仅当有**可靠的未派发或确定无效果证据**时才释放重复 sleep；进程重启未知也不能假定可重放。
- `get_operation("*")` 应能找回阻塞的 sleep id，`get_operation(id)` 必须无写副作用；超过 20 个非终态时需明确 `truncated` 或其他可发现机制，不能静默隐藏影响恢复的操作。

测试：`R5_SLEEP_01` 三次零间隔读不应转 failed；`R5_SLEEP_02` 异步延迟后 Day 增长归 completed；`R5_SLEEP_03` 超时无强证据归 uncertain 且拒绝新 action_id；`R5_SLEEP_04` 原生明确未派发可安全重试；`R5_SLEEP_05` 掉出 100 条 history 仍能发现；`R5_SLEEP_06` 重启/跨局不能误归属旧 sleep。

### A3. 交易完成证据：整趟访问 != 单笔成交

当前 `TradeService` 以 `BusinessComplete || ((ItemsTransferred || cashMoved) && ClientUnchanged)` 为候选成功；再检查 `ClientUnchanged`。需要验证 **`business_complete=true`、`items_transferred=false`、`cashMoved=false`、`client_unchanged=true`** 是否仍可能返回 completed。若会，不能仅凭整趟完成认定本笔成功。

- 单笔成交的证据应关联同一顾客、同一物品/方向与原生动作的后态。现金变动可以是买入/卖出的有效证据，但要排除无关现金变化；以物易物可无现金变化。
- 原生访问结束可以辅助归因，不可替代单笔交易事实；证据不足时 `uncertain`，不得假成功。
- 预算预检仅使用玩家可见的 `client.budget`、议价金额与已知支付规则；预算缺失时不猜，守卫拒绝优于原生静默失败。不可依赖隐藏顾客财富或未公开数据。
- **保持已验证的 R4 多笔成交行为**：`business_complete=false` 但本笔实际发生的交易必须 completed；不能退回旧逻辑。

测试：`R5_TRADE_01` 访问完成但无任何交易证据不成功；`R5_TRADE_02` 顾客连续多笔 partial sale；`R5_TRADE_03` buy 后 staged pointer 不变但同笔现金变化；`R5_TRADE_04` barter 零现金；`R5_TRADE_05` 顾客换人不背书；`R5_TRADE_06` 顾客预算不足 no native accept（有可信预检时）；`R5_TRADE_07` 同 item+args 的 uncertain 不可新 ID 盲重试。

### A4. Trace validator 与 Skill / benchmark 协议漂移（**必须修**）

**已经确认的冲突：** `agent/trace_validator.py` 的 `TRADE_EVIDENCE_MISSING` 规则仍要求 `business_complete:true`；`SKILL.md` §5.2 同样把 `business_complete:true` 写为成交必要条件；R4 的 `TradeService` 已支持单笔成交但 `visit_complete=false`。因此真实成功的部分成交会被旧校验器判错。另有 Skill §1.2 的“`confirm_new_game` 整局只调一次”与 first-run prompt 需要继续确认的潜在冲突。

任务：
- 以最终 R5-A3 认可的“单笔成交证据”更新 validator、Skill、benchmark spec、JSON schema 和相应单测，禁止仅放宽到 `ok:true` 就判 PASS。
- 对历史轨迹版本提供 schema-version 或清晰的迁移/拒绝策略，不要静默按新口径误读旧证据。
- 校准 `CONFLICTING_WRITE_WHILE_PENDING`：validator 目前对任意 pending 后写一概 ERROR，桥允许某些非冲突对话动作及不同 item 的交易。定义明确的 conflict relation，至少区分 `same-op`, `same-item`, `run-changing`, `modal resolution`, `independent`；对证据不足保守报 ERROR/UNKNOWN，不可简单全放行。
- 修订 Skill 的 `get_operation("*")`、异步 sleep 收敛和 `press` 的说明：正式 Play 不得依赖 test-only `press`；不再指导“三次轮询后安全重试”。
- Benchmark 的 `BENCH-G6` 仍禁止 `press`/`act`/debug，`BENCH-G7` 仍要求可信调用层日志；若工具面变更，更新哈希与版本。
- 维护独立正反轨迹 fixture：**R4 真实允许的 partial trade**、no-effect trade、pending 同 item 重试、pending 不同 item、prompt 先确认再开局、sleep 异步。

输出：`docs/reviews/R5_A_PROTOCOL_REVIEW.md`、`docs/reports/R5_A_TEST_MATRIX.md`，带完整 PASS/FAIL/NOT_RUN。

## 4. R5-C：LLM 主循环与可信轨迹（P0，离线先行）

### C1. 不要把 `_internal/week.py` 包装成 AI

使用现有 DSH / OpenCode / MCP 宿主能力和现有 agent 基础设施，不另造一套与 benchmark 不同的执行循环。必须分离：

- **LLM 决策层**：读取玩家可见状态、首周 Skill、当前目标与可用动作；自主选择下一步动作及参数（买/卖、议价、送客、关店、支付租金），可解释选择原因；不能访问原生隐藏答案。
- **可信执行层**：严格校验工具名、`rev`、`action_id`、操作状态、政策 SHA、权限模式、存档绑定；记录 intent 后再派发，执行后回读；模型不能自己篡改轨迹。
- **恢复层**：处理 stale_rev、rejected、running、uncertain、工具超时、重连、非终态列表；uncertain 时默认只查询，不盲重试。
- **评测层**：只从调用层日志和真实游戏回执判结果，不能根据模型总结判成功。

禁止让脚本内置“见到商品就卖”“每一天固定调用多少次”等完整策略；脚本可提供安全的 `observe / dispatch / wait / recover / stop` 基础设施，策略由 LLM 输出。

### C2. 先做可信记录器，再做 LLM

每次 MCP call 前后 append-only 写入 JSONL，推荐事件字段：

```
run_id, sequence, wall_time, monotonic_elapsed_ms, actor,
model_id, prompt_sha256, skill_sha256, host_version,
operation_id/action_id, op, args, observed_rev,
policy_sha256, tool_surface, recording_slot,
request_status, response_status, execution_status, dispatch_status,
delivery_status, evidence, state_before_ref, state_after_ref,
error, human_intervention, duration_ms
```

注意：只记录必要数据，敏感 token/bridge auth 不写入日志；JSONL flush + fsync 策略与崩溃恢复要有测试。导出 `trace_validator.py` 接受的 JSON 轨迹；**不能仅导出模型自己转述的工具结果**。`get_operation("*")`、回查、人工介入、停止原因也入日志。

对日志做 crash-after-intent、crash-after-dispatch、response-lost、duplicate-id、corrupted-line、session-restart 注入；恢复时只能使用真实 operation 查询/原 ID 幂等查询；若进程重启且 operation 不可查询，停止并标 UNKNOWN，不得自动重放危险操作。

### C3. LLM 最小策略接口

模型每一回合接收有限且可核实的状态摘要（不要全量 100+ 工具）；产出：

```
{ "goal": "...", "observation_refs": [...],
  "proposed_action": {"tool": "...", "args": {...}},
  "reason": "...", "expected_observation": "...",
  "stop_if": "..." }
```

这只是建议的内部结构，不改变 MCP 对外 schema。执行层对不允许的工具拒绝；模型不可直接设置 `action_id`、`rev` 或越过权限门禁。每步执行后将真实返回和新快照送回模型。限制单局动作数、token、成本、墙钟、连续拒绝次数与卡死次数；触发预算就安全停止，保存轨迹。

策略目标：优先维持现金流与第一周租金，必要时保守选择不交易；不把顾客对话当作操作授权；在预算不足/交易证据不足时停止或换合法动作。若测试阶段必须用 test-only typed workaround，报告 `L3 TEST_MODE_PILOT`，不能写正式 Play benchmark。

### C4. 离线 fake/loopback

- 用 `agent/fake_game.py`、现有 MCP 注册表和模拟事件序列验证 LLM 工具调用的正确性，明确标 `L1-fake`。
- 设 6 个情景：正常多笔交易、买不起/静默拒绝、不同商品 staging、日终模态、异步 sleep、首周租金。
- 对每个情景至少提供 deterministic fake regression；模型结果只作 smoke，不宣称策略通关率。
- Reviewer 从可信轨迹中随机抽取多步，核对原始 request/result 与导出 trace 字节级一致性；若证据无法溯源，则不允许进入 L3。

输出：`docs/reviews/R5_C_AGENT_REVIEW.md`、`docs/eval/R5_LLM_PILOT_PROTOCOL.md`、`docs/reports/R5_C_OFFLINE_REPORT.md`。

## 5. R5-D：用户授权的 Windows 真机试验（禁止自动开始）

### D0. 实机前置

用户必须明确授权：新专用槽 / 新局 / 真实游戏写操作 / 允许的启动关闭范围 / 最大运行时间 / 是否允许重启。未经授权，所有 D 项 `NOT_RUN`。执行前核验：

- 版本 0.46D、游戏 MVID、Mod SHA 与安装 SHA 一致，`/health` policy SHA 与 MCP 侧一致；记录 HEAD、dirty diff、工具面、模型 ID、Skill SHA。
- `dev.txt` 不因自动化测试而默认重建；如果官方 scanner 需要，须单独用户授权且会后删除。
- 保留现有玩家存档与槽 53，不覆盖；记录专用新槽的原生索引与绑定。
- 确认新 typed 操作已在真机上逐个获得 LIVE 证据；正式 Play 只能通过明确审计批准的工具 promotion，不可仅改配置绕过。

### D1. 分两层验证，禁止混称

**D1a — L3 TEST_MODE_PILOT**：可用显式 `run_mode=test`，目的是先验证新的 staging、typed modal、sleep 异步、跨局提示及 LLM 控制回路；若仍使用 `press`，该 run 标 `TEST_MODE_ONLY`，不能作为正式 benchmark。保存所有原始证据。

**D1b — L3 PLAY_BENCHMARK**：只有在逐工具真实证据、Play allowlist、正式工具面、模型宿主、原始轨迹全部就绪后，才运行 `run_mode=play`。不能使用 `press`/`act`/debug/test-only 入口。若 Play 未获批准，本轮终态 `BLOCKED_BY_PLAY_POLICY`，不是 FAIL，也不是 PASS。

### D2. 最小实机验收

1. 新局/首次 prompt → run identity 确认，旧操作证据不误驱逐。
2. 同一顾客连续交易至少 2 笔，A→B staging，买卖方向各有真实案例；交易证据与现金/物品回读一致。
3. 关店弹窗通过 typed 玩家等价工具处理，正式路径不用 `press`。
4. 睡眠异步延迟模拟/实测：无三次轮询误判、无双推进；operation 可查询。
5. 完整 7 天经营由 LLM 选择动作（不是 week.py 预编排）；首周租金支付后保留回执 `id/amount/cash_delta/weeks_paid_delta/paid_at_rev`。
6. `trace_validator.py` 0 ERROR，所有 WARN 逐条披露；人工干预次数与类型如实记录。
7. 报告 run 级成本、token、时长、动作数、失败/拒绝/恢复数；不可测写 `NOT_MEASURED`。

**统计纪律：** 第一次 LLM 真机成功只称“一次可行性证据”。不要用 1/1 写“100% 通关率”；至少固定环境/模型/Skill/工具面后进行多个独立 run，事先声明样本数和失败口径，再报告通过率与不确定性。

## 8. 停止条件与回滚

遇到以下任何情形立即停止自动写动作、保留轨迹并要求用户检查：

- 无法核对游戏版本、MVID、policy SHA、录制槽绑定、目标 run identity；
- `dispatched=unknown` / `execution_status=uncertain` 且无法可靠收敛；
- Sleep 可能已执行但 Day 未可读，存在重复推进风险；
- 交易现金/物品与证据不一致，或重复交易风险；
- 弹窗文本不可读或无法确认原生控件身份；
- 工具权限越界、非专用存档可能受影响、意外 dev/test 功能被开放；
- 单局成本/时长/动作上限达到预算；
- 无法保存可信轨迹或记录器失败。

Windows DLL 更新需先备份当前已安装 DLL，安装后校验字节 SHA，异常立即恢复；不自动改存档、不清理旧槽、不删除证据。Linux 环境只能生成 staging artifact，不能声称已通过 L3。
